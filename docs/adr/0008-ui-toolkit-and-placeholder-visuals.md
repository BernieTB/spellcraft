# 0008. UI Toolkit screens, placeholder 2D shapes and a single bootstrap scene

- **Status:** Proposed
- **Date:** 2026-10-03

## Context

The Vertical slice needs real game screens: the run screen where fights play out, the level-up choice, the boss
preparation and the recap (issues #73, #77, #84, #85, #88). Until now the only screen is the debug fight viewer,
drawn with IMGUI (`OnGUI`), which is fine for a developer tool but not for a player-facing game.

Constraints:

- The project is built with Claude Code, which cannot see the editor. Anything authored through the inspector
  or as scene/prefab YAML is fragile (CLAUDE.md, rule 7). Screens should be text files that can be read, diffed
  and reviewed.
- The art pipeline is an open question in the GDD. The art direction is "warm 2D, flat colours, ink/pen look",
  but no asset exists and none should be invented now.
- The game targets Windows PC only, with mouse and keyboard.

On 2026-10-02 the owner decided: game screens use **UI Toolkit**, and fights use **simple 2D shapes** until the
art pipeline is decided (issue #65). The screen and scene structure was left to this ADR.

## Decision

**UI technology: UI Toolkit.** Every game screen is a UXML file (layout) plus USS files (style), written as text
and loaded by a `UIDocument`. Screen code queries named elements (`root.Q<Label>("title")`) and fills them from
Core state; it holds no game rules (CLAUDE.md, rule 2).

**Placeholder visuals: simple 2D shapes.** Until the art pipeline is decided, fights and screens use flat-colour
shapes drawn by UI Toolkit (boxes, bars, borders): health and shield bars, highlighted cards, plain text. No
sprites, no imported art, minimal animation (USS transitions at most). Colours and sizes live in USS, not in C#.

**Scene structure: one bootstrap scene, screens switched in code.**

- `Assets/_Project/Unity/Scenes/Bootstrap.unity` is the only scene in the build settings. It holds a camera, the
  `GameBootstrap` entry point and one `UIDocument` with the shared `PanelSettings`.
- Moving from one screen to another replaces the document's content in code (a new UXML tree), instead of
  loading another scene. Later screen tickets add a small screen host for this; the first screen only sets the
  title.
- The scene is generated by an editor script (`BootstrapSceneBuilder`), never edited by hand.

**Layout.** UI code stays in the `Game.Unity` assembly, under `Unity/UI/`:

| Path | Content |
|---|---|
| `Unity/UI/*.cs` | Screen views (`Game.Unity.UI`), one per screen |
| `Unity/UI/Screens/` | One UXML file per screen |
| `Unity/UI/Styles/` | USS files: `Common.uss` holds the shared colour and size variables |
| `Unity/UI/Themes/` | `GameTheme.tss`, the runtime theme (imports Unity's default theme) |
| `Unity/UI/GamePanelSettings.asset` | Shared `PanelSettings` (generated) |
| `Unity/Scenes/Bootstrap.unity` | The bootstrap scene (generated) |

A separate UI assembly is not created yet: screens need the content assets and the bootstrap, both in
`Game.Unity`, and a split would create a reference cycle. It can be extracted later if the UI grows.

**The debug fight viewer stays on IMGUI.** It is an editor-only tool, kept out of builds by the placeholder
build check, and does not need to move.

## Consequences

### Positive

- Screens are plain text (UXML/USS), so Claude Code can write, review and diff them, and EditMode tests can load
  a screen and check its elements without Play mode.
- Styling is centralised in USS variables: swapping the placeholder palette for the final art direction is a
  style change, not a code change.
- One scene keeps the build settings and scene YAML minimal, and screen flow is ordinary, testable code.

### Negative

- This setup uses screen-space overlay UI only: fight visuals are UI elements, not sprites. World-space UI, or
  animated sprites and particles if the art pipeline needs them, would need a camera layer or panel set up for
  that later.
- The owner, not Claude Code, has to check the look in the editor or a build; tests only prove the structure.
- With a single scene, every screen shares one `PanelSettings` and one document; screens must clean up what they
  register when they are replaced.

## Alternatives considered

- **uGUI (Canvas):** mature and well documented, but layouts live in scene/prefab YAML built in the inspector,
  which Claude Code cannot see or safely edit.
- **IMGUI (`OnGUI`):** already used by the debug viewer and fully code-driven, but it is an immediate-mode
  developer UI: hard to style, no layout engine worth the name, not suited to player-facing screens.
- **Text-only screens:** the fastest, but they cannot show the spell line, health bars or card highlights that
  make the fights readable.
- **One scene per screen:** each screen would be isolated, but every screen adds scene YAML and a build settings
  entry, and passing run state between scenes needs a persistent object anyway. A single scene with code-driven
  screens is simpler for a small game.
